# ฟังก์ชัน 7: เขียนสคริปต์ → teleprompter

## 0. ตัวตนช่อง Agent-M (อ่านก่อนทุกครั้ง)
ช่องเปลี่ยนแนวเป็น **"นักสืบดิจิทัลและผู้ถอดรหัสเสียงปริศนา" (Digital & Audio Forensics)** แผนเต็มอยู่ที่ `reports/channel-strategy-agent-m.md` ในโปรเจกต์ davinci-bot ให้อ่านทุกครั้งก่อนเขียน เพราะผู้ใช้อาจแก้แผนในไฟล์นั้น
- **ผู้เล่าเรื่อง:** นักสืบสายเทคที่เป็นทั้ง programmer และ musician พิสูจน์ด้วยเครื่องมือจริง ไม่ใช่แค่เล่า (ยังเป็น "ผม...ครับ" แบบเพื่อนเล่าเรื่องตามเดิม)
- **3 แกนเนื้อหา:**
  1. **Audio & Signal Anomalies:** สัญญาณวิทยุ เสียงปริศนา คลื่นความถี่กับจิตวิทยา (UVB-76, เสียงใต้มหาสมุทร, Havana Syndrome)
  2. **Cryptography & Internet Mysteries:** โค้ดลับ ปริศนาออนไลน์ Dark Web การตามล่าแฮกเกอร์ (Cicada 3301 ฯลฯ)
  3. **Tech Disasters & Digital Forensics:** โศกนาฏกรรมจากซอฟต์แวร์หรือระบบ (Y2K, บั๊กระบบการบิน, ransomware)
- **โหมดเรื่อง (ใช้คู่กับ story engine ใน skill ผู้ใช้):**
  - คดีแฮก/ปล้นด้วยมัลแวร์ → ปฏิบัติการ หรือ ไล่ล่า
  - ปริศนาโค้ด/สัญญาณที่ยังไม่มีคำตอบ → ปริศนาที่ยังไม่คลี่คลาย + **"ไขรหัสไปพร้อมคนดู"** (ให้คนดูลองเดาก่อนเฉลยแต่ละชั้น)
  - หายนะทางเทคโนโลยี → **"โซ่เหตุการณ์"** ไล่ทีละข้อว่าข้อไหนขาด (แบบ "โซ่ 5 ข้อ" ในเรื่องน้ำท่วม)

### เทคนิคประจำช่อง (ต้องมีในทุกสคริปต์)
1. **Show, Don't Tell = ช่วงสาธิตจริงหน้ากล้อง** อย่างน้อย 1–3 ช่วงต่อคลิป ให้เขียนเป็นบล็อกแยกในสคริปต์:
   ```
   [DEMO: <ชื่อช่วง> | เครื่องมือ: Terminal/Python/Spectrogram/DAW/กีตาร์/คีย์บอร์ด | ~เวลา]
   สิ่งที่ทำบนจอ: ...ทีละขั้น (ให้ host ทำตามได้จริง)...
   🎙️ ต้องพูด: ...ประโยคที่ผูกกับเรื่อง...
   💬 พูดด้วยคำตัวเอง: ...ระหว่างพิมพ์/เล่น...
   ผลที่คนดูจะเห็น: ...(ตัวเลข กราฟ เสียง ที่เป็นหลักฐาน)...
   ```
   - การสาธิตต้อง**จำลองและปลอดภัย** เช่น สคริปต์ Python สั้นๆ ที่ brute-force ล็อก 3 หลักของตัวเอง, ดู spectrogram ของไฟล์เสียงสาธารณะ, เล่นโน้ตบนคีย์บอร์ดเทียบกับความถี่ที่วัดได้ หรือ diff ไฟล์ log ตัวอย่าง
   - โค้ดในสคริปต์ต้องสั้น อ่านง่าย รันได้จริง และใส่ไว้ในภาคผนวก "โค้ด/ไฟล์สำหรับ DEMO" ด้วย (ใช้แจกสมาชิกได้)
   - **"Show" ไม่ได้แปลว่าต้องลงมือสาธิตเองเสมอ (กฎจากผู้ใช้):** ผู้ใช้ไม่ชอบ DEMO ที่ต้องมานั่งจำลองบนเครื่องตัวเองทุกครั้ง ถ้าช่วงไหนทำสดแล้วไม่สนุก/ไม่ปลอดภัย/เยิ่นเย้อ ให้เปลี่ยนเป็น **"เล่าให้เห็นภาพ + ตัวอย่างจริง + ภาพประกอบ"** แทนได้ คือ (ก) อธิบายด้วยคำเปรียบที่เห็นภาพ (ข) ยกเคสจริงที่มีเอกสาร/ข่าวรองรับมาขยาย — ค้นข้อมูลจากแหล่งอื่นได้ เช่น ฉาก "รหัสผ่านว่าง" ของ Half-Life 2 เสริมด้วยเคส Mirai botnet 2016 — และ (ค) ใช้กราฟิกทำเอง + B-roll/ฟุตเทจข่าวจากแหล่งอื่น (ส่งฟังก์ชัน 3 เช็กลิขสิทธิ์, ข่าว = 🟡 ใช้สั้นแบบ fair use + เครดิต) ตัวเลข/ข้อมูลจากเคสเสริมต้องอ้างแหล่งและกำกับให้ถูก (เช่น "ยอดติดเชื้อ" ≠ "ยอดอุปกรณ์ทั้งหมด") ให้ถามหรือดูบริบทผู้ใช้ก่อนว่าจะเอาแบบลงมือสาธิต หรือแบบเล่า+ภาพประกอบ — ค่าเริ่มต้นเลือกแบบที่เล่าสนุกและปลอดภัยกว่า
2. **The Ticking Clock:** ฉากโค้ดหรือการเจาะระบบต้องมีนาฬิกา เช่น เวลาที่เหลือ, จำนวนเครื่องที่ติดเพิ่มต่อนาที หรือเงินที่ถูกโอนออก แล้วตัดสลับคู่ขนาน ผู้โจมตี / ผู้ป้องกัน / คนที่โดนผลกระทบ ตาม scene architecture ของ skill ผู้ใช้
3. **Visual Metaphors:** ศัพท์เทคนิคทุกคำครั้งแรกต้องมาพร้อมภาพเปรียบเชิงพฤติกรรมในชีวิตประจำวัน (เช่น brute force = ปั๊มกุญแจแสนดอกมาไขประตูรัวๆ) และ**คำเปรียบหลักของตอน**ต้องปูไว้ตั้งแต่ต้น แล้วกลับมาเฉลยตอนท้าย
4. **เสียงคือหลักฐาน (ความสามารถนักดนตรี):** ถ้าเรื่องเกี่ยวกับเสียง ให้มีช่วงให้คนดู "ฟัง" จริง เช่น เสียงต้นฉบับ → ตัดความถี่ → เทียบโน้ต และเขียน cue ให้ฟังก์ชัน 4 ว่า `[SOUND: …]` โดยแยกเสียงหลักฐานออกจากดนตรีประกอบให้ชัด
5. **กราฟิกสำหรับทีมตัดต่อ:** ใส่ `[UI: terminal/หน้าจอระบบจำลอง — …]` และ `[ภาพ: …]` ตรงจุดที่ต้องใช้ เพื่อให้ editor ทำ UI/Terminal animation ได้ตรง
6. **ของสำหรับสมาชิก:** ท้ายสคริปต์ให้ระบุสิ่งที่แจกสมาชิกได้ เช่น ซอร์สโค้ดของ DEMO, ไฟล์เสียง raw (เฉพาะที่สิทธิ์อนุญาต) หรือ checklist OSINT ที่ทำซ้ำได้อย่างถูกกฎหมาย

### กฎความปลอดภัยสำหรับเนื้อหาไซเบอร์และเสียง (เพิ่มจาก Step 4 ของ skill ผู้ใช้)
- เล่าระดับ **"เกิดอะไรขึ้น ทำไมได้ผล และป้องกันยังไง"** ห้ามให้ขั้นตอน exploit ที่ใช้ได้จริง, โค้ดมัลแวร์, วิธีเข้า dark web หรือตลาดผิดกฎหมาย, หรือวิธีหลบการตรวจจับ
- DEMO ต้องทำกับระบบหรือไฟล์ของตัวเอง หรือข้อมูลสาธารณะเท่านั้น และพูดบนจอให้ชัดว่าเป็นการจำลอง
- **OSINT:** ห้ามแกะรอยหรือเปิดเผยข้อมูลส่วนตัวของบุคคลทั่วไปที่ไม่ใช่บุคคลสาธารณะในคดี และห้าม doxx แม้ข้อมูลจะหาได้
- เรื่องที่วิทยาศาสตร์ยังถกเถียง (เช่น Havana Syndrome) ต้องแยก "ยืนยันแล้ว / สมมติฐาน / ถูกหักล้างแล้ว" และใช้เอกสารทางการเป็นแกนตามข้อ 3
- ชื่อแฮกเกอร์หรือผู้ต้องสงสัย ใช้ได้เฉพาะที่ศาลหรือหน่วยงานเปิดเผยแล้ว (ตามกฎบุคคลจริงของ skill ผู้ใช้)

## 0b. รูปแบบ input ที่ผู้ใช้ส่งมา (ทุกครั้ง)
ผู้ใช้จะส่งตาราง 3 คอลัมน์ ทั้งแบบแถวเดียวและหลายแถว:

| หมวดหมู่ | หัวข้อคอนเทนต์ (Hook/Title ตัวดึงความสนใจ) | การเปรียบเทียบ/การเล่าเรื่อง (Agent-M Style) |
|---|---|---|

แต่ละคอลัมน์ใช้แบบนี้:
- **หมวดหมู่** → เลือกแกนเนื้อหาและโหมดเรื่อง (ข้อ 0) แล้วบอกใน creative brief
- **หัวข้อคอนเทนต์** → ใช้เป็นชื่อคลิปหรือเชื้อของ hook แต่ hook ยังต้องเปิดด้วย "วันนี้เราจะมาพูดถึงเรื่อง..." และปิดด้วยประโยคส่งเข้าเรื่อง (ข้อ 2) โดยหัวข้อในประโยคเปิดต้องชวนสงสัยและไม่สปอยล์ แล้วเสนอชื่อคลิป 2–3 แบบใน production notes
- **การเปรียบเทียบ/การเล่าเรื่อง** → ใช้เป็น**คำเปรียบหลักของตอน** (ข้อ 3 ของเทคนิคประจำช่อง) ปูไว้ในช่วง setup ใช้ซ้ำในฉากสำคัญ และเฉลยหรือพลิกในตอนท้าย ห้ามใช้แค่ครั้งเดียวแล้วทิ้ง

**ถ้ามีหลายแถว:** ทำ creative brief สั้นของทุกแถวก่อน (แถวละ 6–8 บรรทัด) แล้วถามว่าจะให้เขียนเต็มแถวไหนก่อน จากนั้นเขียนทีละเรื่อง แยกไฟล์ตามโฟลเดอร์เรื่อง

**ถ้าคอลัมน์ไหนว่าง:** เสนอค่าที่ดีที่สุดให้เลือก 2–3 แบบ แล้วเลือกตัวที่แนะนำไว้ก่อน (ไม่ต้องหยุดถาม ยกเว้นหมวดหมู่หรือหัวข้อว่าง)

## 1. กฎการเขียน = skill ของผู้ใช้เอง (ห้ามเขียนกฎซ้ำที่นี่)
- กฎทั้งหมด (โหมดเรื่อง, hook, scene architecture, ความปลอดภัยเรื่องบุคคลจริง, ความยาว, Shorts, live, lessons log) มาจาก skill **action-story-channel-script** ของผู้ใช้
- ให้ใช้**เวอร์ชันล่าสุด**เสมอ:
  1. หาไฟล์ด้วยคำสั่ง `ls -t ~/.claude/skills/synced/*/action-story-channel-script/SKILL.md ~/.claude/skills/*/SKILL.md` แล้วเลือกไฟล์ที่ `name:` เป็น action-story-channel-script และแก้ไขล่าสุด (ปัจจุบันคือชุดที่ sync จาก claude.ai)
  2. อ่านทั้งไฟล์ด้วย Read ก่อนเริ่มเขียน (หรือเรียกผ่าน Skill tool ถ้ามีให้ใช้)
- **ลำดับความสำคัญเมื่อกฎขัดกัน:**
  1. คำสั่งล่าสุดของผู้ใช้ในแชท
  2. กฎที่ผู้ใช้สั่งเพิ่มไว้ในหน้านี้ (ข้อ 0, 0b, 2, 3, 4 และความยาว)
  3. skill action-story-channel-script
  4. ค่าเริ่มต้นอื่นๆ
- กฎอื่นทั้งหมดของ skill ผู้ใช้ยังใช้ตามเดิม เช่น คำต้องห้าม "จิ๊กซอว์", scene architecture, บทสนทนาจำลอง และ Shorts

## 1b. เช็กลิสต์เกลาสำนวนก่อนส่งทุกครั้ง (กฎจากผู้ใช้ — สำคัญ รวมบทเรียนจริง)
ผู้ใช้เกลาสคริปต์ EP. คดี Half-Life 2 มาหลายรอบ บทเรียนทั้งหมดต่อไปนี้ให้ใช้เป็นเช็กลิสต์ไล่ทีละข้อ **ก่อนส่งทุกครั้ง** (หลายข้อ `grep` ช่วยได้)

### A. อย่าให้ทุกตอนฟังเหมือนเทมเพลตเดียวกัน
1. **ตัวอย่างในสกิล = โครงสร้าง ไม่ใช่บทให้ลอก** ประโยคอย่าง "คดีนี้มีเรื่องแปลกเยอะครับ แปลกจนถ้าเอาไปเขียนเป็นนิยายคงโดนบอกว่าเกินจริง" หรือ "ก่อนจะเข้าเรื่อง ผมอยากพาย้อนไปปี… เพราะโลกตอนนั้นไม่เหมือนตอนนี้เลย" เป็นแค่ตัวอย่างของ D.B. Cooper **ห้ามคัดมาใช้ซ้ำในเรื่องอื่น** ให้เขียนประโยคจริงขึ้นใหม่จากรายละเอียดเฉพาะของเรื่องนั้นทุกครั้ง (ประโยค "ทำไมคดีนี้แปลก", ประโยคปูเรื่อง/ย้อนอดีต, ประโยค plant/callback)
2. **ตัวเปิดแต่ละฉากต้องไม่ซ้ำคำ** ห้ามขึ้นต้นฉากด้วยคำเดิม (เช่น "ทีนี้…") ติดกันหลายฉาก ให้สลับระหว่าง คำถาม / cross-cut cue / ประโยคหักมุม / สรุปสั้น ก่อนส่งให้ `grep` ไล่ดูตัวเปิดทุกฉาก ถ้าเจอคำเดิมเกิน 2 ฉากให้แก้
3. **ข้อยกเว้นที่ต้องคงไว้** คือลายเซ็นช่องจริง 2 จุดเท่านั้น: ประโยคเปิด "วันนี้เราจะมาพูดถึงเรื่อง…" และประโยคส่งเข้าเรื่องท้าย hook (ข้อ 2) ที่เหลือต้องสดใหม่

### B. ภาษาพูดต้องเข้าใจง่ายและเป็นธรรมชาติ
4. **ใช้คำพูดที่เป็นธรรมชาติแบบพูดจริง** เช่น "เสี่ยงติดคุก" ไม่ใช่ "เสี่ยงคุก" อ่านออกเสียงแล้วต้องลื่นแบบที่คนพูดจริง
5. **ห้ามใช้ศัพท์ที่คนฟังทั่วไปไม่รู้จักโดยไม่แปล** เช่น อย่าใช้ "แชสซี" ให้ใช้ "โครงรถ" ถ้าจำเป็นต้องใช้ศัพท์เทคนิค ให้มีคำแปลหรือภาพเปรียบในชีวิตประจำวันกำกับทันที — เทียบว่าคนที่ไม่มีพื้นฐานฟังครั้งเดียวต้องเข้าใจ
6. **อย่าบรรยายกระบวนการเล่าของตัวเอง** ตัดประโยค meta แบบ "เล่าเป็นภาพให้เห็นนะครับ", "ผมขออธิบายให้ชัดเลยว่า…", "เดี๋ยวผมจะเล่าให้ฟังว่า…" ทิ้ง เข้าเนื้อหาตรงๆ — ถ้าต้องเกริ่นว่าจะแวะอธิบายศัพท์ ให้เบาและสั้น เช่น "ผมขอแวะอธิบายคำว่า… นิดนึงนะครับ" พอ ไม่ต้องขยายว่าสำคัญแค่ไหน/เป็นพระเอกของเรื่อง

### C. อธิบายให้ได้ความรู้จริง
7. **ศัพท์เทคนิคสำคัญ: อธิบายเชิง technical ให้ลึกก่อน แล้วค่อยยกภาพเปรียบ** ห้ามให้แค่ภาพเปรียบลอยๆ ช่องนี้ขายความเข้าใจจริง ให้บอกก่อนว่าสิ่งนั้นทำงานยังไงจริงๆ (ยาวได้ถ้าจำเป็นให้คนดูได้ความรู้) แล้วปิดด้วยภาพเปรียบในชีวิตประจำวันเป็นตัวตอกย้ำ เช่น อธิบาย game engine ว่าคือซอฟต์แวร์แกนกลางที่ทำ rendering/ฟิสิกส์/เสียง (พร้อมแปลว่าแต่ละอย่างคืออะไร) ก่อน แล้วค่อยเทียบ "เครื่องยนต์กับโครงรถ"

### D. อย่าสั่งคนดู ให้เขารับรู้เอง
8. **ห้ามสั่งให้คนดูจำ** เลิกใช้ "จำคำว่า X ไว้นะครับ" หรือ "เก็บไว้ในใจก่อนนะ เดี๋ยวมันจะกลับมา" (จิตวิทยา: คนไม่ชอบถูกสั่ง) ให้ปูข้อมูลให้ชัดในจังหวะที่เล่า แล้วคนดูจะจำเองเวลามันกลับมา — **ข้อยกเว้น:** callback แบบ *ถามให้นึก* ตอนเฉลย ("จำได้ไหมครับว่า…") ใช้ได้ เพราะเป็นการชวนนึกถึงสิ่งที่เล่าไปแล้ว ไม่ใช่สั่งให้ท่องจำล่วงหน้า

### E. ทุกประโยคต้องยืนได้ด้วยตัวเอง (หัวฉากไม่ได้ถูกอ่าน)
9. **หัวฉาก `## [ฉาก N] …` และทุกอย่างในวงเล็บเหลี่ยม `[…]` ไม่ใช่บทพูด** host ไม่ได้อ่านออกเสียง (teleprompter ตัดทิ้งหมด) เพราะงั้นบทพูดห้ามพึ่งหัวฉาก เช่น ห้ามเปิดฉากว่า "ขอหยุดอธิบายอีกนิด เพราะ**คำนี้**สำคัญ" เพราะคนฟังไม่รู้ว่า "คำนี้" คือคำไหน — ต้องเรียกชื่อสิ่งนั้นออกมาตรงๆ ("คำว่าซอร์สโค้ดที่ผมเพิ่งพูดถึง…") ไล่เช็กทุกประโยคที่มี "คำนี้ / เรื่องนี้ / ตรงนี้ / อันนี้" ว่ามีคำนามชัดเจนอ้างอิงในประโยคก่อนหน้าไหม
10b. **อย่าปล่อยปฏิกิริยา/อารมณ์ให้ลอย — ระบุเสมอว่าใครรู้สึกหรือใครทำ** ห้ามเขียน "มันน่าขนลุก", "น่าตกใจมาก", "ไม่น่าเชื่อ" ลอยๆ ให้บอกชัดว่าใครเป็นคนรู้สึก ("พอเจอสาเหตุ ทั้ง Gabe กับทีมงานถึงกับขนลุก") และบอกด้วยว่ารู้สึกกับอะไร เช่นเดียวกับกริยาที่ไม่มีประธานชัด
10. **callback ต้องชี้ไปยัง plant ที่มีจริง โดยเฉพาะหลังแก้ hook** ถ้าแก้ hook หรือฉากต้นๆ แล้ว ให้ `grep` หา "เกริ่นไว้ / ที่ผมบอกไป / ตั้งแต่ต้น / จำได้ไหม" ทุกจุด แล้วเช็กว่าสิ่งที่อ้างยังอยู่ในบทจริง ถ้า plant หายไป ให้ย้ายไป "ตั้งชื่อ/ปู" ใหม่ในฉากที่พูดถึงแทน อย่าปล่อยให้ callback ลอย

## 1c. แกนเรื่อง (story core) — เขียนก่อนสคริปต์ทุกครั้ง (กฎจากผู้ใช้)
ผู้ใช้วิเคราะห์ฟุตเทจตัวเองแล้วพบว่าที่เล่าไม่เป็นธรรมชาติ เพราะ**อ่านบทโดยยังไม่เข้าใจแกนเรื่องลึกพอ** (สะดุดในประโยคที่ซับซ้อน, ขึ้นต้นใหม่กลางประโยค, หยุดก่อนชื่อเฉพาะ) ผู้ใช้จึงต้องการไฟล์ให้**อ่านเพื่อเข้าใจ** แล้วเอาไปเรียบเรียงเล่าด้วยคำของตัวเอง สคริปต์เต็มยังทำเหมือนเดิม แต่ใช้เป็นบทอ้างอิงและแหล่งของประโยคที่ต้องพูดตรงเป๊ะ

**ลำดับงาน:** fact-sheet → **แกนเรื่อง** → สคริปต์ (สคริปต์ต้องเล่าตามโซ่เหตุผลเดียวกับแกนเรื่อง) ถ้าผู้ใช้สั่ง "แกนเรื่องอย่างเดียว" ให้หยุดที่แกนเรื่อง

**ไฟล์:** `~/Desktop/Agent-M/<ชื่อเรื่อง>/<topic>_core_vN.md`

**ภาษาในไฟล์นี้:** เป็นภาษาอธิบายให้เพื่อนที่ฉลาดแต่ไม่รู้เรื่องนี้อ่าน ไม่ใช่บทพูด
- ไม่ใช้ "ครับ" และไม่มีลีลาหรือ cliffhanger
- 1 ประโยค = 1 ความคิด และเอาเรื่องที่เกิดขึ้นขึ้นก่อนคำอธิบาย
- ทุกเหตุการณ์ต้องตอบได้ว่า**ทำไม** ห้ามเล่าแค่ว่าเกิดอะไรขึ้น
- ใช้ bullet และตารางได้เต็มที่ ควรอ่านจบได้ภายใน 10–15 นาที

**โครงสร้าง (เรียงตามนี้):**
1. **เรื่องนี้ในประโยคเดียว:** ใคร ทำอะไร เพราะอะไร แล้วลงเอยยังไง
2. **เล่าให้เพื่อนฟังใน 30 วินาที:** 4–6 ประโยค ภาษาพูดง่ายๆ ทั้งเรื่องตั้งแต่ต้นจนจบ รวมตอนจบด้วย (ไฟล์นี้เฉลยได้หมด)
3. **ทำไมคนดูต้องสนใจ:** เดิมพันคืออะไร ใครเสียอะไร และเรื่องนี้เกี่ยวกับชีวิตคนดูยังไง
4. **ตัวละคร:** ตาราง ชื่อ | **คำอ่านภาษาไทย** | เป็นใคร | ต้องการอะไร | ทำไมถึงทำแบบนั้น | ลงเอยยังไง
5. **โซ่เหตุและผล (หัวใจของไฟล์):** เขียนเป็นข้อเรียงกัน โดยแต่ละข้อต้องเชื่อมกับข้อก่อนหน้าด้วยคำว่า **"เพราะ / เลย / แต่ / ดังนั้น"** ห้ามใช้ "แล้วก็…" ถ้าข้อไหนเชื่อมด้วยเหตุผลไม่ได้ แปลว่ายังเข้าใจเรื่องไม่พอ ให้กลับไปค้นต่อ ตัวอย่าง:
   - Valve ใช้รหัสผ่านอ่อนบนเครื่องในออฟฟิศ **เลย**ทำให้แฮกเกอร์เข้ามาได้
   - **แต่** แฮกเกอร์ไม่ได้อยากได้เงิน **เพราะ**เป็นแฟนเกม…
6. **ไทม์ไลน์:** ตาราง วันที่ | เหตุการณ์ | แหล่ง (ป้าย A/B/C ตามข้อ 3) ใช้เป็นข้อมูลอ้างอิง
7. **แนวคิดเทคนิคที่ต้องเข้าใจจริง:** ทุกคำที่เรื่องต้องใช้ ให้อธิบายครบ 5 ข้อ
   - มันคืออะไร
   - ทำงานยังไง (ลึกระดับที่ host ตอบคำถามคนดูในคอมเมนต์ได้)
   - ทำไมสำคัญกับเรื่องนี้
   - ภาพเปรียบในชีวิตประจำวัน
   - คำถามที่คนดูน่าจะถาม พร้อมคำตอบ
8. **จุดหักมุมและอารมณ์:** แต่ละช่วงของเรื่อง คนดูควรรู้สึกอะไร และอะไรที่ทำให้รู้สึกแบบนั้น
9. **สิ่งที่ยังไม่ชัดหรือยังถกเถียงอยู่:** แยกให้ชัดว่าอะไรยืนยันแล้ว อะไรเป็นคำบอกเล่า และอะไรยังไม่มีใครรู้ เพื่อไม่ให้ host พูดเกินหลักฐานตอนเล่าด้วยคำตัวเอง
10. **🎙️ ต้องพูดตรงเป๊ะ:** รายการสั้นๆ ของตัวเลข ชื่อ (พร้อมคำอ่าน) วันที่ คำกำกับทฤษฎี และประโยคลายเซ็นช่อง (ข้อ 2) ส่วนอื่นนอกจากนี้ host เล่าด้วยคำตัวเองได้ทั้งหมด
11. **เช็กความเข้าใจ:** คำถาม 6–10 ข้อ โดยเน้นคำถาม "ทำไม" และ "ถ้า…จะเกิดอะไรขึ้น" ซ่อนคำตอบไว้ใน `<details>` ถ้า host ตอบได้โดยไม่เปิดดู ถือว่าพร้อมเล่า
12. **การ์ดคิวสำหรับอัด (beat card):** แบ่งตามฉากของสคริปต์ ใช้หัวฉากเดียวกัน ฉากละ 3–5 bullet เป็น**คำสำคัญ ไม่ใช่ประโยค** (เช่น "รหัสผ่านว่าง → เข้าเครื่อง → เจอโค้ด") พร้อม 🎙️ ของฉากนั้น ใช้วางแทน prompter เวลาที่ host อยากเล่าเอง

**เช็กก่อนส่ง:**
- ทุกข้อในโซ่เหตุและผลต้องมีคำเชื่อมเชิงเหตุผล
- ชื่อเฉพาะทุกชื่อต้องมีคำอ่านภาษาไทย
- ตัวเลขทุกตัวต้องตรงกับ fact-sheet
- ห้ามคัดลอกประโยคจากสคริปต์มาใส่ เพราะไฟล์นี้ต้องอธิบาย ไม่ใช่ซ้อมบท

## 2. รูปแบบ hook ประจำช่อง (บังคับทุกสคริปต์วิดีโอ)
ผู้ใช้กำหนดให้ hook เปิดและปิดด้วยรูปแบบเดียวกันทุกตอน:
1. **ประโยคแรกของสคริปต์:** `วันนี้เราจะมาพูดถึงเรื่อง [หัวข้อ]` ตรงตามคำนี้ทุกคำ ใช้ครั้งเดียว และหัวข้อต้องสั้นและชวนสงสัยตามกฎของ skill ผู้ใช้
2. **เนื้อ hook:** ตาม hook recipe ของ skill ผู้ใช้ ได้แก่ เหตุผลที่เรื่องนี้แปลก → ข้อเท็จจริงที่ชวนสงสัย 2–3 ข้อ → คำถามหลัก → teaser ของสิ่งที่เจอทีหลัง → lead-in (ชื่อคดี หรือคนที่เราจะตามดูผ่านสายตา)
   - **hook ต้องจับใจความได้ตั้งแต่ฟังรอบแรก (กฎจากผู้ใช้):** ให้บอก**ชื่อจริง**ของสิ่งสำคัญ — ชื่อบริษัท/องค์กร, ชื่อเกมหรือของกลาง, ชื่อตัวละครหลัก — พร้อม**อธิบายสั้นๆ ว่าแต่ละอย่างคืออะไร** (เช่น "บริษัทเกมชื่อ Valve เจ้าของเกม Half-Life", "ซอร์สโค้ด ก็คือพิมพ์เขียวทั้งหมดของเกม") และสรุปให้ชัดว่า**เกิดอะไรขึ้น** ห้ามเลี่ยงชื่อด้วยคำลอยๆ อย่าง "บริษัทนึง / เด็กคนนึง / ของบางอย่าง" จนคนฟังจับต้นชนปลายไม่ถูก
   - การบอกชื่อและอธิบายว่าอะไรเป็นอะไร **ไม่ใช่การสปอยล์** สิ่งที่ห้ามเฉลยคือจุดหักมุม/ตอนจบ (เช่น กับดักจับกุม, คำตัดสิน, ตัวตนที่ยังเป็นปริศนา) ส่วนฉาก setup ปูชื่อได้เต็มที่
3. **ประโยคสุดท้ายของ hook = ประโยคส่งเข้าเรื่อง** สั้น เป็นประโยคเดียว ลงท้ายด้วย "ครับ" และไม่มีข้อมูลใหม่หลังจากนั้น เลือกจากชุดนี้ หรือสำนวนใกล้เคียงในรูปแบบเดียวกัน:
   - "เดี๋ยวเราไปดูกันครับ"
   - "ไปฟังกันเลยครับ"
   - "ไปดูกันเลยครับ"
   - "เดี๋ยวเราไปฟังกันครับ"
   - ต่อท้าย lead-in ได้ เช่น "…ผ่านสายตาของแอร์โฮสเตสที่ชื่อทีน่า เดี๋ยวเราไปดูกันครับ"
   - **ห้ามใช้ประโยคเดียวกันทุกตอนติดกันเกิน 3 ตอน** ให้สลับในชุดนี้เพื่อไม่ให้ฟังเป็นสูตร
4. หลังประโยคส่งเข้าเรื่อง ตามด้วย `[INTRO / โฆษณา]` (ถ้ามี) แล้วจึงเข้าฉากปูเรื่อง
5. Shorts ไม่ต้องใช้รูปแบบนี้ ให้ตามกฎ Shorts ของ skill ผู้ใช้
6. **ตรวจก่อนส่งทุกครั้ง:** `make_prompter` คืนค่า `hook_check` (เปิดถูกไหม / ปิดด้วยประโยคส่งเข้าเรื่องไหม) ถ้าไม่ผ่าน ให้แก้ก่อนส่ง

**กติกา**
1. ทุกข้อใน fact-sheet ต้องติดป้ายแหล่ง เช่น `[A: MH370 SIR 2018 น.440 §3.2]` หรือ `[B: Reuters 2018-07-30]` ถ้าหาได้แค่ชั้น C ให้เขียน `[C: ยังไม่ยืนยันจากต้นทาง]` แล้วพยายามหาต่อ ห้ามใช้ข้อมูลนั้นเป็นจุดเฉลยหรือตัวเลขบนจอ
2. ใช้ `official_doc`:
   - `info` ดูสารบัญ
   - `search` หาหน้าที่มีข้อความ
   - `text` **อ่านทั้งหน้าก่อนอ้าง** ห้ามอ้างจาก snippet อย่างเดียว
3. **ก่อนดาวน์โหลดเอกสาร** ให้บอกผู้ใช้ว่าเป็นเอกสารอะไร หน่วยงานไหน ขนาดประมาณเท่าไหร่ แล้วรออนุมัติ
4. เอกสารภาษาอังกฤษ ให้แปลไทยแบบคงความหมาย บนจอใส่ประโยคต้นฉบับคู่กับคำแปลได้
5. เอกสารขัดกับข่าว: เชื่อเอกสารทางการ แต่ถ้ามีข้อโต้แย้งที่ถูกบันทึกไว้ ให้เล่าเป็นข้อโต้แย้งตามกฎของ skill ผู้ใช้
6. ท้ายสคริปต์ต้องมี **ตารางแหล่งข้อมูล**: เอกสาร | หน่วยงาน | ปี | หน้าที่ใช้ | ลิงก์ (เฉพาะลิงก์ที่เปิดดูแล้วจริง) | ใช้ในฉาก
7. ตัวอย่างเอกสารชั้น A ของเรื่องในช่อง:
   - MH370: Safety Investigation Report โดย Malaysian ICAO Annex 13 Safety Investigation Team (ก.ค. 2018) และ ATSB "The Operational Search for MH370" (ต.ค. 2017)
   - DB Cooper: แฟ้มคดีใน FBI Vault
   - ซาริน: เอกสารกระทรวงยุติธรรมญี่ปุ่น และรายงานวุฒิสภาสหรัฐ ปี 1995
   - น้ำท่วม: รายงานของกรมอุตุนิยมวิทยา, สสน. และ ปภ.

## 4. เล่าด้วยเอกสารจริงให้สนุก (ร้อยเรียง ไม่ใช่อ่านรายงาน)
1. **เอกสารคือหลักฐานบนโต๊ะ:** จุดเฉลยสำคัญให้โชว์เอกสารจริงบนจอ เช่น "ในรายงานฉบับสุดท้าย หน้า 440 เขียนไว้แค่ประโยคเดียว…" → อ่านคำแปล → **หยุด 1 จังหวะ** ให้คนดูอ่านไฮไลต์บนจอ
2. **ร้อยเรียงเป็นฉาก:** ใช้ตาราง ภาคผนวก และ timeline ในรายงานเป็นวัตถุดิบของ scene architecture แต่เล่าเป็นเหตุการณ์ (ใคร ทำอะไร ที่ไหน เวลาไหน) ห้ามเล่าเรียงตามสารบัญรายงาน ศัพท์เทคนิคให้แปลเป็นภาพเปรียบเทียบในชีวิตประจำวัน
3. **ช่องว่างในเอกสารคือปมที่ดีที่สุด:** สิ่งที่รายงานบอกว่า "ไม่สามารถระบุได้", ส่วนที่ถูกปิดทึบ (redaction) หรือคำถามที่รายงานไม่ได้ตอบ ใช้เป็น open loop ได้ แต่ห้ามเติมคำตอบเอง
4. **คำพูดตอนเกิดเหตุ เทียบกับข้อสรุปในรายงานทีหลัง** คือดราม่าที่เป็นข้อเท็จจริงล้วน ให้วางไว้ในฉากที่เรื่องนั้นมีผล พร้อมบอกว่ารู้เมื่อไหร่ (ตามกฎลำดับเวลาของ skill ผู้ใช้)
5. **ใช้พอดี:** ใช้เอกสาร 1–3 ประโยคต่อฉาก ห้ามอ่านยาว ตัวเลขชุดใหญ่ให้ทำเป็นการ์ดตัวเลข และใส่ "เอกสารจริง" 1 ครั้งต่อช่วงสำคัญ เพื่อให้แต่ละครั้งมีน้ำหนัก
6. **รูปแบบ visual cue ในสคริปต์:** `[เอกสาร: <ชื่อเอกสาร> หน้า N — ไฮไลต์ "<ประโยคตรงตามต้นฉบับ>"]` ฟังก์ชัน 3 จะทำเป็น insert อัตโนมัติ (ภาพทั้งหน้าแล้วซูมเข้าไฮไลต์เหลือง) ส่วนเครดิตบนจอใช้รูปแบบ "ที่มา: <หน่วยงาน>, <ชื่อรายงาน> (ปี) หน้า N"
7. **สิทธิ์การใช้:** ตรวจหน้าลิขสิทธิ์ของเอกสารทุกฉบับ ตามแนวทางคร่าวๆ ดังนี้
   - เอกสารรัฐบาลกลางสหรัฐ (FBI, NTSB, Senate) โดยทั่วไปเป็น public domain
   - ATSB ส่วนใหญ่เผยแพร่แบบ CC BY ต้องใส่เครดิต
   - เอกสารรัฐบาลอื่น ให้แสดงบางหน้าเพื่ออ้างอิงหรือวิจารณ์ พร้อมเครดิต และใส่สถานะสิทธิ์ (🟢/🟡) ในตารางแหล่งข้อมูล

## 5c. สร้างบทความเว็บคู่กับสคริปต์เสมอ (กฎจากผู้ใช้)
ทุกครั้งที่เขียนสคริปต์เรื่องหนึ่งเสร็จ ให้**สร้างบทความเว็บของเรื่องนั้นให้ด้วยเป็นค่าเริ่มต้น** (ไม่ต้องรอให้ผู้ใช้ขอ) เพราะผู้ใช้เอาไปโพสต์บนเว็บไซต์ของตัวเองคู่กับคลิป

1. **คนละ register กับสคริปต์:** บทความเป็น**ภาษาเขียน** (ไม่ใช่ "ผม...ครับ" แบบพากย์) อ่านเอง มีหัวข้อ ย่อหน้าเรียบเรียง ใช้ fact-sheet ชุดเดียวกับสคริปต์ และ**คงคำกำกับความถูกต้องทุกจุดเหมือนสคริปต์** (ตัวเลขที่ยังไม่ยืนยัน, คำบอกเล่า vs เอกสารทางการ, กฎความปลอดภัยไซเบอร์ที่ไม่ลงขั้นตอนทำซ้ำได้) ขึ้นต้นด้วยกล่องหมายเหตุ disclaimer และปิดท้ายด้วย**รายการแหล่งอ้างอิง**
   - **แหล่งอ้างอิงต้องใส่ลิงก์ที่คลิกได้ (markdown link) และใส่เฉพาะ URL ที่เปิดดูจริงแล้วเท่านั้น** ห้ามเดา/ประกอบ URL เอง ถ้าเข้าต้นฉบับโดยตรงไม่ได้ ให้ลิงก์แหล่งที่คัดข้อความไว้แล้วกำกับว่า "อ้างผ่าน…" และท้ายรายการเขียนกำกับว่าลิงก์ทั้งหมดเปิดตรวจแล้ว ณ วันที่เรียบเรียง (ตามกฎข้อ 3 เรื่องลำดับชั้นแหล่งข้อมูล)
2. **ไฟล์ที่ต้องสร้าง 2 ไฟล์** เก็บในโฟลเดอร์เรื่องเดียวกัน:
   - `<topic>_article_vN.md` — บทความเต็มแบบ standalone มี YAML front matter (`title`, `description`, `slug`, `tags`, `author: "Agent-M"`, `date`, `cover_image`)
   - `<topic>_article_webform_body.md` — เฉพาะ**เนื้อหา Markdown** สำหรับก๊อปวางช่อง "เนื้อหา" ของฟอร์มเว็บ (ตัด front matter และหัวข้อ H1 ชื่อเรื่องออก เพราะฟอร์มมีช่องแยก — เริ่มที่กล่องหมายเหตุแล้วเข้าเนื้อหาเลย)
3. **แล้วในแชตให้ map ค่าทุกช่องของฟอร์มเว็บผู้ใช้ให้พร้อมก๊อป** ฟอร์มมีช่องเหล่านี้:
   - **ชื่อบทความ\*** — ชื่อบทความ (เขียนเชิง SEO ได้ ไม่ต้องเป็นชื่อคลิป)
   - **Slug (URL)** — แนะนำ slug อังกฤษอ่านง่าย (เว้นว่างได้ ระบบสร้างจากชื่อ รองรับไทย)
   - **TL;DR — คลิปนี้ได้อะไร** — bullet 4–6 ข้อว่าผู้อ่าน/ผู้ดูได้อะไร
   - **เนื้อหา (Markdown)** — ชี้ไปไฟล์ `_article_webform_body.md` (ใส่ขั้นตอน/โค้ด/ลิงก์ tool หรือ affiliate ได้ตรงนี้ ถ้าเรื่องมี DEMO ให้สรุปขั้นตอนปลอดภัยแบบไม่ใช่ exploit ทำซ้ำ)
   - **YouTube Video ID** — ปกติยังไม่มีตอนเขียน ให้เว้นว่าง บอกผู้ใช้ว่าเอารหัสหลัง `watch?v=` มาใส่ทีหลัง
   - **รูปหน้าปก** — ผู้ใช้อัปโหลดเอง เสนอว่าใช้ภาพอะไรดี (ต่อ broll-research ได้)
   - **ราคา (บาท)** — ค่าเริ่มต้นแนะนำ `0` (ฟรี) เพราะบทความดึงคนจากคลิป; คอนเทนต์พิเศษ (เช่น ซอร์สโค้ด DEMO) เก็บไว้ขายในซีรีส์แทน
   - **แท็ก** — ดึงจากแกนเนื้อหา + คีย์เวิร์ดของเรื่อง
   - **ซีรีส์ / ลำดับในซีรีส์** — แมปกับเพลย์ลิสต์ของช่อง (เช่น "แฟ้มคดีไซเบอร์", "แฟ้มคดีเสียงคลื่นความถี่") เสนอค่า
   - **สถานะ\*** — แนะนำ `Draft` ก่อน แล้วค่อยเปลี่ยนเป็น `Published` ตอนปล่อยคลิป
   - **เวลาเผยแพร่** — เวลาไทย (Asia/Bangkok) ตั้งให้ตรง/หลังเวลาปล่อยคลิป; เว้นว่าง = ยังไม่โผล่หน้าแรก
   - **ภาษา\*** — `ไทย`
   - **Translation group ID** — เสนอค่า slug-based (เช่น `hl2-leak-2003`) เพื่อใช้ซ้ำกับเวอร์ชันอังกฤษในอนาคต
4. **ความยาวบทความ:** ค่าเริ่มต้นประมาณ 1,500–2,500 คำไทย อ่านจบใน ~7–10 นาที ถ้าผู้ใช้อยากได้สั้น/ยาวกว่านี้ค่อยปรับ
